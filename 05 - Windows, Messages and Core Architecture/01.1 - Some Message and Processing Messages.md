Messages are handled in the user defined `Window Procedure` function whose definition is already done by Microsoft as following:

```c
LRESULT CALLBACK WndProc(HWND hWnd, UINT msg, WPARAM wParam, LPARAM lParam) {
	// Your code
	return DefWindowProc(hWnd, msg, wParam, lParam);
}
```

## Some Messages

1. `WM_CREATE` - This is the message that is inserted first time when the window is about to be created this allows user to load content, handle context for some application that may require it (like OpenGL).
2. `WM_PAINT`: This messages is inserted to the queue after the `WM_CREATE` message and informs the program when part or all of the window client area is invalid or must be updates which means that it must be redrawn or painted. Read more here [[01.2 - WM_PAINT|WM_PAINT]]
3. `WM_CLOSE`: This message is a signal to the program that the program should prepare for closing, or totally ignore it, its totally on program what should be done, should it proceed or cancel the process. Read more on [[01.3 - WM_CLOSE|WM_CLOSE]]
4. `WM_DESTROY`: This message is a signal that the window will be destroyed now and unlike `WM_CLOSE` program can't stop this process, now only thing that program can do is to make sure necessary cleanup is done, like cleaning the memory, saving some data et cetera. Read more [[01.4 - WM_DESTROY|WM_DESTROY]].
5. `WM_QUIT`: This message is not related to any window, this message indicates that the message loop should be stopped and the program should exit. Read more [[01.5 - WM_QUIT|WM_QUIT]].

## Queued and Nonqueued messages

Messages can either be queued or nonqueued. 

1. The queued messages are those that are placed in a program’s message queue by Windows
2. The nonqueued messages are the results of calls by Windows directly to the window procedure

### The Asynchronous Path: Queued Messages

When a user interacts with physical hardware—such as pressing a key or moving a mouse—the hardware interrupts the CPU. The Windows Kernel intercepts this physical electrical signal and translates it into a digital structure called a "Message" (e.g., `WM_MOUSEMOVE`).

However, the operating system cannot force the application to process this mouse movement immediately. The application might be busy calculating a complex mathematical equation. If the OS interrupted the application to force the mouse movement, data corruption could occur.

To solve this, the OS uses a [[01 - Core architectural overview#Message Queue and Loop|Message Queue]].

- **Posting:** The OS "posts" the message into a specific area of memory assigned to your application's thread. It places the message at the back of a line (the queue) and leaves it there.
- **The Loop:** Your program contains a `while` loop that continuously executes the `GetMessage` function. This function checks the queue. If a message is present, it retrieves it and passes it to `DispatchMessage`, which then routes it to your Window Procedure (`WndProc`).

### 2. The Synchronous Path: Non-Queued Messages

Not all messages originate from slow, unpredictable human hardware. Many messages originate from within the operating system itself, demanding immediate execution.

For example, if the user resizes a window, the OS must immediately calculate the new dimensions and inform the application. It cannot wait for the application's message queue to slowly process a backlog of mouse movements.

To achieve instant execution, the OS uses the **Non-queued** pathway.

- **Sending:** The OS completely bypasses the Message Queue and the `GetMessage` loop.
- **Direct Invocation:** The OS Kernel directly invokes your Window Procedure (`WndProc`) function. It simply points the CPU's instruction pointer directly to the memory address of your `WndProc`, executing it immediately just like a standard C function call.
- The OS halts its own thread progression until your `WndProc` finishes processing the non-queued message and executes a `return` statement.
