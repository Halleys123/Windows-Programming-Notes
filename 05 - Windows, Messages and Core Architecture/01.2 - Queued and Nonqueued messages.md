
Messages can either be queued or nonqueued. 

1. The queued messages are those that are placed in a program’s message queue by Windows
2. The nonqueued messages are the results of calls by Windows directly to the window procedure

### The Asynchronous Path: Queued Messages

When a user interacts with physical hardware—such as pressing a key or moving a mouse—the hardware interrupts the CPU. The Windows Kernel intercepts this physical electrical signal and translates it into a digital structure called a "Message" (e.g., `WM_MOUSEMOVE`).

However, the operating system cannot force the application to process this mouse movement immediately. The application might be busy calculating a complex mathematical equation. If the OS interrupted the application to force the mouse movement, data corruption could occur.

To solve this, the OS uses a [[01 - Core architectural overview#Message Queue and Loop|Message Queue]].

- **Posting:** The OS "posts" the message into a specific area of memory assigned to your application's thread. It places the message at the back of a line (the queue) and leaves it there.
- **The Loop:** Your program contains a `while` loop that continuously executes the `GetMessage` function. This function checks the queue. If a message is present, it retrieves it and passes it to `DispatchMessage`, which then routes it to your Window Procedure (`WndProc`).

### The Concurrency Mandate: Preventing Interface Paralysis

Modern Windows architectures utilize [[Windows NT and Windows 98#^771638|Pre-Emptive multitasking]] (introduced following the limitations of early systems like [[Windows NT and Windows 98]]). Under this system, the operating system kernel acts as a strict timekeeper, forcibly dividing CPU cycles among competing programs to ensure that no single application can halt the entire machine. However, this macroscopic safety net protects the operating system, not the internal mechanics of your specific application.

Every window is sustained by a primary thread whose sole responsibility is to operate the message loop. This thread is the critical communication bridge between the user, the hardware, and the graphical interface.

If a programmer assigns a massive, time-consuming calculation directly to this primary thread, the thread is immediately captured by the mathematics. Because execution is sequential, the thread physically cannot return to the `while` loop to execute the `GetMessage` function.

The consequence is immediate interface paralysis. If the user attempts to drag the window by its title bar, the operating system dutifully generates the corresponding movement messages and places them into the application's queue. But because the primary thread is occupied by the calculation, the queue is ignored. The messages sit unread. The window visually freezes, incapable of redrawing itself or responding to human interaction, even while the CPU is working at maximum capacity.

There is a proper way to handle this which will be discussed later.

### 2. The Synchronous Path: Non-Queued Messages

Not all messages originate from slow, unpredictable human hardware. Many messages originate from within the operating system itself, demanding immediate execution.

For example, if the user resizes a window, the OS must immediately calculate the new dimensions and inform the application. It cannot wait for the application's message queue to slowly process a backlog of mouse movements.

To achieve instant execution, the OS uses the **Non-queued** pathway.

- **Sending:** The OS completely bypasses the Message Queue and the `GetMessage` loop.
- **Direct Invocation:** The OS Kernel directly invokes your Window Procedure (`WndProc`) function. It simply points the CPU's instruction pointer directly to the memory address of your `WndProc`, executing it immediately just like a standard C function call.
- The OS halts its own thread progression until your `WndProc` finishes processing the non-queued message and executes a `return` statement.

>[!important]
>Messages Loop and Window Procedure do not run concurrently, so that means at a time one message is processed of-course unless some hardware interrupt happens then your program is a secondary choice for the OS.

>[!fact] Static Variable Trap
>If you declare a static variable inside the Window Procedure, then that is guaranteed to retain the value (more specifically retain the latest updated value), unless you call some window function maybe like `UpdateWindow`. 
>Then there is no guarantee that variable have the latest value, that happens because when you call this function control goes back to kernel and kernel may decide that to process this we need a new message and in such cases processing of that message occurs instantly creating a `pseudo recursion` like situation.
