This is the second message that is inserted in the queue, it informs that program that a part of client area or whole client area is `invalid` or must be updated either due to a window creation, resize, closing, minimizing of window or manual invalidation by the user. For more information about [[01 - Introduction#Painting and Repainting|strict execution flows of WM_PAINT read here]].

`Invalid` in above context holds a special meaning, by Invalid client area in windows programming, it is meant that program has not yet drawn anything on the window or the thing that were drawn are now not valid either due to resize or minimize or overlap.

To launch a WM_PAINT message when the window is resized you must set the [[02.1 - WNDCLASS Styles#^b2c598|CS_HREDRAW and CS_VREDRAW]] bits in [[02.1 - WNDCLASS Styles|WNDCLASS Styles]].

## Scenario when WM_PAINT is added to queue

1. A previously hidden area of the window is brought into view when a user moves a window or uncovers a window. 
2. The user resizes the window (if the window class style has the CS_HREDRAW and CW_VREDRAW bits set). 
3. The program uses the [[ScrollWindow]] or [[ScrollDC]] function to scroll part of its client area.  ^bb2f0a
4. The program uses the [[InvalidateRect]] or [[InvalidateRgn]] function to explicitly generate a WM_PAINT message ^58e7bb

There are cases when window is partially covered in those cases **windows try to save the area** and restore it later although it is not always successful in doing so.

1. Windows removes a dialog box or message box that was overlaying part of the window. 
2. A menu is pulled down and then released. 
3. A tool tip is displayed

There are cases in which **windows surely saves the area** when the window is being overlapped with some other element which are:

1. The mouse cursor is moved across the client area. 
2. An icon is dragged across the client area.
## Handling WM_PAINT

The program should be structured enough to accumulate *required* information to draw necessary elements on screen because the screen is getting cleared every frame (game development) or on every WM_PAINT message.

For processing of WM_PAINT you almost always begin by getting a [[03 - Device Context|Device Context]] even when using libraries like Direct2D or OpenGL you still need to start by getting a [[03 - Device Context]]

>[important] What not to do?
>case WM_PAINT: 
>	return 0 ; // WRONG

Windows places a WM_PAINT message in the message queue because part of the client area is invalid. Unless you call [[03 - Device Context#Begin and End paint|BeginPaint]] and [[03 - Device Context#Begin and End paint|EndPaint]] (or similar function function as explained in [[03 - Device Context]], Windows will not validate that area. Instead, Windows will send you another WM_PAINT message, and another, and another, and another...

When Processing WM_PAINT you should use [[03 - Device Context#`BeginPaint` Function|BeginPaint]] to get [[03 - Device Context|Device Context]] and not other functions like [[03 - Device Context#`GetDC` and `ReleaseDC`|GetDC]]. Read about why here.
