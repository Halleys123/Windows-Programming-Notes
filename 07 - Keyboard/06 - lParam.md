## Repeat Count

To understand the "Repeat Count," you have to understand what happens when a user physically holds down a key, and how Windows prevents your application from choking to death on the resulting flood of data.

### 1. The Typematic Rate (Hardware Spammer) 

When you hold down a key (like the `Down Arrow`), the keyboard doesn't just send one signal. After a short delay, the hardware starts spamming the OS with repeated keystrokes. This speed is called the **Typematic Rate** (configurable in Windows settings, often around 30 repeats per second).

### 2. The Bottleneck (Why Repeat Count > 1) 

Imagine your application is currently executing a heavy UI redraw. It takes 50 milliseconds to finish. During those 50ms, the user is holding the `Down Arrow`. Because of the typematic rate, the keyboard hardware generates three separate `WM_KEYDOWN` interrupts.

Windows intercepts these three keystrokes. It looks at your Application Message Queue and realizes: *"This application's thread is busy. If I drop three individual `WM_KEYDOWN` messages into the queue, the queue will get bloated."* **The Optimization:** Instead of adding three separate messages, Windows looks to see if there is already an unprocessed `WM_KEYDOWN` for that exact key sitting in your queue. If there is, it just updates that existing message by incrementing its **Repeat Count** by 3. Windows essentially batches the physical presses into a single logical message.

## OEM Scan Code

- The OEM Scan Code is the code generated by the hardware of the keyboard
- We don’t need this stuff anymore. Windows programs can almost always ignore the OEM Scan Code except when dependent on the physical layout of the keyboard maybe if using a Piano, Casio or unique keyboard style.

## The Extended Key Flag

To understand the Extended Key Flag, we have to look at another hardware evolution: the transition from the original 1981 IBM PC keyboard to the legendary 1985 IBM Model M (the 101-key "Enhanced" keyboard). 
### The Historical Hardware Problem

On the original 83-key IBM keyboard, there was no separate cluster of arrow keys. The arrow keys and navigation keys (Home, End, Page Up, Page Down) were physically shared with the Numeric Keypad on the right side. You had to toggle `Num Lock` off to use the arrows, and toggle it on to type numbers.

In 1985, IBM released the Enhanced Keyboard. They added a brand new, dedicated cluster of navigation keys between the letters and the numpad, plus an extra `Enter` key on the numpad, and an extra `Ctrl` and `Alt` key on the right side of the spacebar.

**The Engineering Challenge:** For backward compatibility, the new dedicated `Up Arrow` had to send the exact same hardware Scan Code as the old Numpad `Up Arrow` (which was the physical '8' key).

If both keys sent the same Scan Code, how could the PC tell them apart?

### The `0xE0` Prefix

To solve this, the keyboard microcontroller was programmed to send a special escape byte `0xE0` immediately *before* the Scan Code whenever an "Enhanced" key was pressed.

When the Windows keyboard driver sees this `0xE0` prefix, it strips it out, translates the Scan Code into a Virtual Key code as usual, but it sets **Bit 24** of the `lParam` in your `WM_KEYDOWN` message to `1`. This is the **Extended Key Flag**.

If you press the dedicated `Up Arrow`, the flag is 1. If you press the Numpad `Up Arrow` (Numpad 8 with Num Lock off), the flag is 0.

### Why do programs "generally ignore it"?

In a standard GUI application, user intent is all that matters. If a user is navigating through a document in a native Win32 Markdown editor, an `Up Arrow` means "move the text cursor up one line." The text editor does not care if the user pressed the dedicated arrow or the numpad arrow; the `VK_UP` Virtual Key code is sufficient to trigger the action.
### When must you NOT ignore it?

You must check the Extended Key Flag when building applications that rely on hyper-specific physical keybinding, such as:

1. **Game Engines:** In competitive first-person shooters, players frequently bind the Left `Alt` key to a completely different action than the Right `Alt` key (e.g., jump-throw binds vs. voice chat). Because both keys generate `VK_MENU`, the only way the game engine knows the difference is by checking if the Extended Key Flag is 1 (Right Alt) or 0 (Left Alt).
    
2. **Virtual Machines / Emulators:** If you are writing software that passes raw keyboard input directly to another operating system, you must accurately reconstruct the exact physical key pressed.

## Context Code

The *Context Code is 1* if the Alt key is depressed during the keystroke. This bit will always
be *1 for the WM_SYSKEYUP and WM_SYSKEYDOWN* messages and *0 for the WM_KEYUP*
*and WM_KEYDOWN* messages, with two exceptions:

1. If the active window is minimized, it does not have the input focus. All key strokes generate `WM_SYSKEYUP` and `WM_SYSKEYDOWN` messages. If the `Alt key` is not pressed, the Context Code field is set to 0. Windows uses `WM_SYSKEYUP` and `WM_SYSKEYDOWN` messages so that a minimized active window doesn’t process these keystrokes.
2. On some foreign-language keyboards, certain characters are generated by combining Shift, Ctrl, or Alt with another key. In these cases, the Context Code is set to 1 but the messages are not system keystroke messages

## Previous Key State

- The Previous Key State is 0 if the key was previously up and 1 if the key was previously down.
- It is always set to 1 for a WM_KEYUP or WM_SYSKEYUP message. , but it can be 0 or 1 for a WM_KEYDOWN or WM_SYSKEYDOWN message

## Transition State
The Transition State is 0 if the key is being pressed and 1 if the key is being released. The field is set to 0 for a `WM_KEYDOWN` or `WM_SYSKEYDOWN` message and to 1 for a `WM_KEYUP` or `WM_SYSKEYUP` message
