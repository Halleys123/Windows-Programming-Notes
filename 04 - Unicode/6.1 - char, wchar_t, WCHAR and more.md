## char Data Type

This data type usually takes 1 byte of storage and uses ASCII character set, In C language a character is declared using `char` data type and a pointer to char presumably takes **4 bytes** if made on a **32 bit system**.

```c
char initial = 'A';
char *name = "Arnav"; // String literal
```

Strings are declared using character array

```c
char name[6] = "arnav\0";
```

To get the the bytes used by a string use `sizeof` operator, it returns the bytes used by an `array` or `struct`.

>[!info]
>The **ISO C Standard** define how many bytes should there be in a data type, but there is no specification about how many bits should there be in a byte.
>
> Read more on **[[02 - ISO C Standard and C Specifications|C Specifications and ISO C Standard]]**

## Wide Characters

[[6 - Wide Characters (The implementation of Unicode)|Wide characters]] are a separate entity from [[#char Data Type]] and don't interfere with each other, wide characters in context of windows can be of two types [[5 - Unicode|Unicode]] and *Multi-Byte Character* which is an implementation of [[4 - Double Byte Character Set|DBCS]]. 
As we know the disadvantages of DBCS it is always better to use Unicode in place of Multi-Byte Character

Wide character functions and implementation are present in the [[01 - Important Windows Headers and DLL's#`WINNT.H` Architecture & Unicode Foundation|WINNT.H Header file]] in windows or, if we see the C standard library they will be present in `wchar.h` or `string.h` headers.

>[!recap]- Why *Multi-Byte Character were bad*?
>There were many reasons but including [[4 - Double Byte Character Set#^3ebee3|Trail Byte]] error and others but in case of windows If you choose Multi-Byte, your program will actually be _slower_ and less efficient. Here is why:
> 
> Since Windows NT, the Windows Operating System kernel natively speaks only 16-bit Unicode. If you set your project to "Multi-Byte," you force your code to compile using the "A" functions (like `MessageBoxA`).
> 
> When your English-only app calls `MessageBoxA("Hello")`, the Windows OS has to:
> 1. Pause your program.    
> 2. Allocate new memory.
> 3. Translate your 8-bit "Hello" into a 16-bit Wide Character `L"Hello"` (using the active Code Page).   
> 4. Pass that newly translated string to `MessageBoxW`.
> 5. Free the temporary memory.
> 
> This process is called **Thunking**. By choosing "Use Unicode Character Set," you skip the translation layer entirely. Your program speaks the kernel's native language, resulting in a cleaner, faster, and more robust Win32 application.


>[!important]- Your choice of implementation
>A software engineer must draw a strict line between internal logic and external communication. While relying on 8-bit Multi-Byte strings is detrimental at the operating system level, an application is not forced to use memory-heavy 16-bit Unicode for its own internal data. To conserve physical RAM, massive text datasets should be processed using highly efficient 8-bit formats. 
>The problem of character encoding only materializes when data crosses the boundary to interact with the OS. Within its own memory space, the application remains sovereign.


### Single Source

When writing program you may want to write the program in Unicode and in ASCII, but that means you need to maintain two different code sources to prevent that Microsoft had implemented a `TCHAR.h` this is like a rewritten version of `stdio.h` because that provide alias for function like 
- `printf` and `wprintf` to `_tprintf` 
- `strcpy` and `wcscpy` to `_tcscpy`

Internal implementation is as following

```C
#ifdef UNICODE
#define _tcslen wcslen
#elif
#define _tcslen strlen
#endif
```
