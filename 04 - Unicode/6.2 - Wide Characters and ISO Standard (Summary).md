Programmers tend to believe that the C programming language is mathematically exact. It is not. The [[02 - ISO C Standard and C Specifications|ISO C Standard]], finalized in the late 1980s based on designs from the 1970s, was built to compile on any machine. Because hardware varied wildly, the rules of the language had to be loose.

The standard states that a `char` is exactly one byte. However, it does not define a byte as eight bits. It requires only that a byte be **_at least_** eight bits. The rules for integers are equally vague. An `int` is not guaranteed to be 32 bits. The standard only dictates a relative hierarchy: a `short` cannot be larger than an `int`, and an `int` cannot be larger than a `long`. It is a system of relationships, not strict measurements.

Hardware, however, does not operate on loose relationships. It operates on physical physics.

A central processing unit (CPU) has a specific "**Word**" size, which dictates the amount of data its internal registers can process in a single clock cycle. The CPU connects to the system's random access memory (RAM) via a physical array of wires known as the Memory Bus. If a memory bus is 32 bits wide, it physically reads memory in exact 4-byte chunks and this size is called the Word size of CPU.

Because of this physical design, data must be aligned correctly in memory. If a 4-byte integer is placed perfectly within a hardware chunk, the CPU fetches it in one cycle. If it is misaligned—spanning across the boundary of two different chunks—the CPU must fetch the first chunk, fetch the second chunk, and mathematically combine them. This doubles the work. The hardware demands exact alignment, which the C standard does not automatically guarantee.

To bridge the gap between a vague language and strict hardware, operating systems enforce their own rules. This is the Application Binary Interface (ABI).

When Microsoft engineers designed the Windows NT kernel, they could not rely on the loose C standard. If a third-party compiler decided an `int` was 16 bits when the operating system expected 32 bits, the system would fail. Microsoft solved this by controlling both the operating system and the compiler. They established an unbreakable rule within their Microsoft Visual C++ (MSVC) compiler: a `long` integer would always be exactly 32 bits.

Using this foundation, they created the `DWORD` (Double Word). A `DWORD` is an alias for an `unsigned long`. Within the Microsoft ecosystem, it is not merely a variable; it is a physical, 32-bit contract enforced by the compiler.

The ABI also dictates mechanical behavior, such as calling conventions. When a program calls a function, variables are pushed onto the CPU's memory stack. The ABI decides who cleans it up. Under standard C rules (`__cdecl`), the program making the call cleans the stack. Under strict Windows rules (`__stdcall`), the function being called is responsible for cleaning its own stack before returning.

This requirement for precision extends to text. The standard 8-bit `char` was sufficient for English, but inadequate for global languages like Japanese or Chinese. Early solutions involved Double-Byte Character Sets, which mixed 8-bit and 16-bit characters. This made counting strings and moving memory pointers mathematically unpredictable.

Microsoft discarded this in favor of `wchar_t` (Wide Character), defined in the Windows API as `WCHAR`. By forcing every character to be exactly 16 bits, they sacrificed memory space to regain mathematical predictability.

Eventually, the global computing community recognized the need for standard precision. In 1999, the C standards committee introduced the `<stdint.h>` header. They did not alter the original `int` or `long` data types, as doing so would break three decades of existing software. Instead, they introduced fixed-width types. When a modern programmer types `uint32_t`, they are no longer guessing. The compiler is legally obligated to find the underlying hardware type that provides exactly 32 bits.

Precision was finally moved from the hands of the programmer to the architecture of the compiler.
